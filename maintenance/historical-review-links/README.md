```sh
# オフライン確認：DB読み取り・書き込みゼロ。通常はこちら。
node scripts/apply-historical-review-links.mjs

# 枠の回復後、必要なら1頭だけ最新データを読む。書き込みなし。
node scripts/apply-historical-review-links.mjs --check-live --limit-horses 1

# 更新を行う際：まず1頭。現時点では実行しない。
node scripts/apply-historical-review-links.mjs --apply --limit-horses 1

# 続きの最大10頭。保存済み分はチェックポイントから除く。
node scripts/apply-historical-review-links.mjs --apply --limit-horses 10
```

通常の再開に `--plan` は不要。絶対パスを指定して実行すれば、作業ディレクトリが別でも使える。待機中の自動ポーリングや429の自動リトライはしない。

読み取り確認は1頭につき1回のドキュメント取得。更新も馬単位でまとめ、必要な馬だけコミットする。書き込みには `archiveUpdatedAt` のサーバー時刻変換も含むため、料金上の書き込み計数とコミット数は同じとは限らない。枠に余裕を持って少数ずつ進める。

## 安全策と実行記録

- 回顧の配列順は使わない。最新DBの名前・コース・評価・本文が一致する唯一の回顧だけ更新。
- 本文変更、同文の重複、別IDの保存、対象レースに別の回顧が存在する場合は保留。準備後に追加・修正された開催日やコース等が準備済みレースと矛盾する場合も保留し、上書きしない。互換のある既存 `raceRef` の追記・型は保持する。準備作成時も回顧自身のメタデータ矛盾を除外する。無理に埋めない。
- 保存するのは回顧内の `raceId` / `raceRef` / `linkVerification` と馬の `archiveUpdatedAt`。SABCD、本文、回顧順、予想データは変更しない。
- Firestoreの元の型を保持し、最新 `updateTime` を条件に更新。同時編集・上限エラーでは止まる。
- 各実行の変更前データ、成功コミット、結果は `.local/historical-review-links/run-*/` に保存。再実行しても以前のバックアップを上書きしない。
- `.local/historical-review-links/checkpoint.json` は成功分・同じIDで保存確認できた分だけ記録。途中停止した場合も再実行でき、コミット直後に処理が落ちても、次回は最新IDを確認して二重保存しない。
- 後日の別タスクでも、まずオフライン確認を実行する。`.local` はgit管理外なので、端末・環境を移す際は一緒に保存する。なくても最新DBの同じIDを確認して安全に再開可能（追加の読み取りは発生する）。
- 新たに成功した分は `checkpoint.json` の内容を確認後 `completed.json` に統合し、`status.json` とこの文書の件数を更新してコミットする。公開索引をDB保存済み記録として代用しない。

全体回顧が未登録のレースや全体回顧側のコース不整合は、このID追加だけで分類・ラップが増えるとは限らない。既存の表示・採点側の矛盾チェックは維持する。
